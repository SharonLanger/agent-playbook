## Shared configuration and credentials — confirmed 2026-11-18

All integrations use the selected shared application YAML and its existing local-overlay/environment precedence. VictoriaLogs has a documented section alongside Langfuse and CrewAI: retain the existing provider-neutral integrations.logging section for its application logging settings. Do not introduce a second overlapping integrations.victorialogs configuration or a provider-specific loader.

Non-secret settings belong in shared application configuration. Tokens, passwords and other secret values belong in the same external secrets file selected by secrets.file, already used for Langfuse credentials and available to other integrations. YAML contains named references rather than literal secrets. Future components follow this same rule.

The current default remains ~/.config/agent-playbook/secrets.env. M3 preserves existing project, package, CLI, file and folder names and user paths; any broader naming migration belongs to issue #56. Shared-secret consolidation uses the existing configured secrets.file path.

The selected direct local VictoriaLogs deployment currently requires no credentials. Document this explicitly; do not invent a token/password or add authentication middleware merely to populate the section. If a later approved deployment needs credentials, it uses the shared secrets mechanism.

### Existing infrastructure discrepancy and migration requirement

Current application documentation explicitly separates Langfuse application keys from app/tooling/observability/.env infrastructure secrets. Therefore the requested shared-file policy is a change to deployment configuration ownership, not a description of completed behavior.

Before implementation, inventory only documented key names and setup/management code, never read personal credential values. Specify how existing Langfuse database passwords, encryption keys and other infrastructure credentials are retained in the selected shared secrets file. Do not regenerate existing values, overwrite unrelated entries, or silently resolve conflicting values. Define an explicit conflict/migration procedure.

Compose receives only the values needed by the selected component through the minimal supported bridge from the existing loader. Shared storage of secrets does not authorize injecting every credential into every container. Avoid another independently editable credentials file, custom parser, credential discovery or config registry. Concrete Compose input mechanics and compatibility with existing Langfuse setup remain to be designed and verified.

## Technical design completion proposal (2026-11-18; awaiting Sharon's concrete approval)

The choices below complete the open technical questions for review. They are proposed contracts, not an extension of the earlier behavioral approval. No runtime change is authorized by this document alone.

### Ownership and entry point

Use two Compose invocations, never `include` or multi-file aggregation: `docker compose -p act-logs -f app/tooling/logging/compose.yaml` and `docker compose -p act-langfuse -f app/tooling/observability/compose.yaml`. A single checkout-only `app/tooling/services/manage.py` coordinates `--start`, `--stop`, `--status` with `--component logs|langfuse|all` (default `all`) and optional `--config PATH`; invoke from the repository root with `app/.venv/bin/python app/tooling/services/manage.py ...`. `all --start` selects enabled integrations; explicit component start still requires its enabled setting. `--stop` addresses the named project even after an integration is disabled; `all --stop` addresses both. Stop and status use Docker's project labels through `docker ps -a --filter label=com.docker.compose.project=<exact-name> --format ...` and `docker stop <verified container IDs>` (bounded `-t 30`), requiring no Compose model, YAML, secrets or manifest. Status reads container State/Health from `docker inspect` and the existing HTTP checks when config is valid; otherwise it reports project/container state without a URL and flags readiness unknown. Stop returns success for no containers and repeats. It never stops IDs whose inspected project label differs. `--status` reports both (or the requested component), including disabled and stopped, without treating disabled as a failure. The entry never runs during workflow execution. Keep the existing `agent-playbook langfuse` CLI spelling and direct `observability/manage.py` path as compatibility entry points delegated to the same component operations; `--check` keeps its existing read-only application check and hosted-endpoint behavior. Existing `--logs`, `--follow`, and `--open` remain Langfuse-only helpers. `--env-file` on the legacy Langfuse CLI/direct helper gives exit 2 with a migration command naming `--legacy-env-file`; it is never an ongoing second store. The direct `python3 app/tooling/observability/manage.py --start` pre-bootstrap mode is retired with explicit bootstrap guidance; the new service entry requires the app venv. Existing CLI `langfuse --check` keeps its Docker-free 0/1/2/3 exits, including disabled 3. `--logs/--follow/--open` continue via the shared component path. This is the narrow M3 bridge, not the M4 management CLI.

`-p` fixes project identity regardless of Compose file top-level `name`, shell `COMPOSE_PROJECT_NAME`, or caller directory. Explicit `-f` and `--project-directory` fix file resolution. Compose is invoked with a deliberately constructed environment (remove inherited Compose control/interpolation variables, then add only required selected values) and `COMPOSE_DISABLE_ENV_FILE=1`; never pass credentials as argv. This explicitly suppresses automatic project/working-directory `.env` loading even when the legacy file is present, per [Compose's documented control variable](https://docs.docker.com/compose/how-tos/environment-variables/envvars/). Keep each definition and its images/services/network/loopback bindings. Logging service name `victorialogs` is unchanged; Docker project is `act-logs`. Langfuse's six service names remain unchanged; Docker project is `act-langfuse`. Compose `config --quiet` validates without printing resolved secrets. Docker's [project-name precedence](https://docs.docker.com/compose/how-tos/project-name/), [interpolation rules](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/), [external volumes](https://docs.docker.com/reference/compose-file/volumes/) and [`down` behavior](https://docs.docker.com/reference/cli/docker/compose/down) support this split. Disposable Compose v2.40.3 probe: a file with `name: legacy-name`, `external: true` volume and interpolated environment resolved under `-p act-logs` to project `act-logs` and the supplied existing volume name; daemon access was unavailable, so no live migration claim.

### Shared loader and minimal schema

Use `app/src/agent_playbook/config/loader.py` and models; extract common base/local selection, `secrets.file` resolution, strict parser and environment precedence into internal helpers used by both workflow `load_configuration` and a narrow `load_local_services_configuration(path, component)` API. It reads selected YAML via `configuration_path`, sibling `.local.yaml`, selected secrets file and process environment in that order. It resolves the selected component only: an explicit logs-only operation does not resolve or require Langfuse project or infrastructure keys, including when Langfuse is enabled in YAML. For `all --start`, first resolve enabled flags with existing overrides, then resolve deployment values for enabled components. For stop/status, resolve selected config for display when possible but inspect project identity regardless of enabled flags; invalid/missing config yields exit 2 for start and a diagnostic for stop/status without blocking safe project inspection. Do not create a provider-specific parser or credentials registry. Keep workflow validation behavior and precedence intact.

Add optional `integrations.langfuse.local_service` containing `minio_port: 9090` and seven named infrastructure references: `postgres_password: {env: POSTGRES_PASSWORD}`, `clickhouse_password: {env: CLICKHOUSE_PASSWORD}`, `redis_auth: {env: REDIS_AUTH}`, `minio_root_password: {env: MINIO_ROOT_PASSWORD}`, `nextauth_secret: {env: NEXTAUTH_SECRET}`, `salt: {env: SALT}`, `encryption_key: {env: ENCRYPTION_KEY}`. This block is relevant only for local deployment; application project `public_key`/`secret_key` remain separate. The Langfuse host port is the port of local loopback `base_url`; reject remote host, path and scheme for **local start** without changing hosted connection checks. The guarded M2 contract keeps seven-day retention fixed in the existing Compose definition; M3 adds no YAML retention field. Logging host port comes from the validated loopback `endpoint`. No VictoriaLogs credential reference is added. Keep fixed container ports, images and paths. Compose receives only `LANGFUSE_PORT`, `MINIO_PORT` plus seven Langfuse infrastructure values for Langfuse, or `LOGS_PORT` for logging, and selected volume identifiers. Make Compose interpolation required for settings supplied by the bridge, eliminating stale defaults; validate bounded port values in the shared models. Add a safe, documented default for optional deployment blocks so old YAML remains loadable. Settings keys and references are documented, never literal secret values.

### Credential consolidation and storage transition

Inventory the seven documented legacy names from tracked `setup.py`/`.env.example`; do not inspect user files in design work. Implementation offers `--migrate` on the shared entry (with optional `--legacy-env-file PATH`, default existing adjacent `.env`) as an explicit pre-start step. No automatic credential generation. Parse legacy file with the existing strict dotenv parser, require all seven nonempty values, and map each fixed legacy name to the corresponding configured `{env: NAME}` reference. Compare each legacy value separately against the **stored** selected shared-file entry at that reference name and against any process override. Identical stored entries remain; different stored or process values stop before mutation and report key names only. A matching process value does not mask a missing/conflicting stored value. Reject duplicate reference names, unsupported control characters/newlines and any reference collision with application project keys. Missing/unreadable/malformed legacy or shared file stops without mutation. Append only missing names atomically using a mode-0600 temporary file in the selected file's directory, flush/fsync, then replace; preserve all unrelated lines/keys and create a private backup before replacement. Serialize accepted values using the strict parser's supported double-quoted escaping, verify parser round-trip in memory before replacing, and never reinterpret characters as shell syntax. A failed write retains original and backup. Do not print values, use shell sourcing, or put values in tracked files. Keep the legacy `.env` untouched as rollback evidence; once migration verifies data, tell the user to remove or archive it manually because it remains a second copy. The old `setup.py` is retained as legacy fixture/tool but not called by new start. A fresh local deployment requires explicit generation into the selected shared secrets file via `--init-secrets`, a one-time safe initializer that writes only absent seven keys, refuses conflicts and preserves unrelated entries; retain existing `secrets.token_hex` sizes. This uses the existing loader/parser and setup generator, with no extra store.

Before **any** `up`, inspect Docker context, old and new project containers by Compose labels, and all expected named volumes. `--migrate --legacy-env-file PATH --legacy-project NAME --config PATH` is explicit; `--legacy-env-file` defaults to the existing adjacent `.env` and `--legacy-project` defaults to the observed `observability` for Langfuse or `agent-playbook-logging-smoke` for logs. Old logging project is `agent-playbook-logging-smoke`, with `agent-playbook-logging-smoke_logs-data`; old Langfuse default project is `observability`, with five `observability_{postgres_data,clickhouse_data,clickhouse_logs,redis_data,minio_data}` volumes. A custom `COMPOSE_PROJECT_NAME` or different recorded project is supported only by explicit `--legacy-project NAME`, verified against container labels and exact mounted volume source/target pairs. Never infer an alternate project from volume name alone. Migration inventory first records exact old container labels, mounted source/target pairs, Docker context and physical volume IDs in a private manifest. It requires old containers to be stopped before inventory; if running, stop with instructions to use legacy `docker compose -p <old-project> -f <component-compose> stop` after backup, then rerun `--migrate`. Once the manifest and credential copy are durable, the operator uses legacy `docker compose -p <old-project> -f <component-compose> --env-file <legacy-file> down` without `-v`; this removes old containers but retains named volumes. New `--start` requires old project containers absent, and refuses any other active writer or old/new project overlap. A stopped old project before `down` is allowed only for migration inventory, never for new `up`. Any partial, foreign, inconsistent or ambiguous volume mapping stops without `up`. For complete old volumes, bind the **existing physical names** in the new Compose files using required `external: true` and `name: ${...}` values. For a clean install, create the required physical volumes (one logging or five Langfuse) explicitly with `docker volume create --label ...`, then verify and bind them; do not claim empty new volumes are migrated data. Existing project never gets a replacement volume silently. Verify no other running container mounts selected volumes, and recheck immediately before `up` to reduce the race; document Docker's lack of an atomic lock and require Docker Desktop not to be operated concurrently. For an existing Langfuse stack, preserve the seven infrastructure values exactly so encrypted database/object data stays readable. `down` is project-scoped and never uses `-v`; no volume rm/prune or reset command is run. Record chosen volume mapping, Docker context, old project, and expected target pairs in a private, non-secret manifest beside the selected secrets file so repeat starts use the same mapping; if manifest and Docker state disagree, fail closed. Stop/status use labels and do not require this file. `--migrate` is repeatable after interruption: compare the durable file and manifest with live state and either finish missing idempotent steps or stop on mismatch. A failed `up` leaves secrets, manifest and volumes untouched for retry. A failed/interrupted secret replacement retains the old file and backup. Rollback: stop the new project with shared `--stop`; verify no act project container is running on mapped volumes; use the retained old `.env`, old Compose definition and old `-p` to run `up -d` with the same named volumes. No old containers need survive `down`. Back up Docker data before the manual transition; live Mac guide checks existing traces/records after restart. A new project name can coexist only when old containers are stopped and storage is uniquely assigned; the old Compose definition and `.env` remain available for rollback after the new project is stopped.

### Exact operator commands (repository root; proposal)

```sh
python3 app/tooling/bootstrap.py
app/.venv/bin/python app/tooling/services/manage.py --status --component all --config app/application.yaml
app/.venv/bin/python app/tooling/services/manage.py --stop --component all
app/.venv/bin/python app/tooling/services/manage.py --migrate --component logs --config app/application.yaml
app/.venv/bin/python app/tooling/services/manage.py --migrate --component langfuse --legacy-env-file app/tooling/observability/.env --legacy-project observability --config app/application.yaml
app/.venv/bin/python app/tooling/services/manage.py --init-secrets --component langfuse --config app/application.yaml
app/.venv/bin/python app/tooling/services/manage.py --start --component logs --config app/application.yaml
app/.venv/bin/python app/tooling/services/manage.py --start --component langfuse --config app/application.yaml
app/.venv/bin/python app/tooling/services/manage.py --start --component all --config app/application.yaml
```

`--migrate` for logs inventories only its old volume; for Langfuse it also consolidates the seven infrastructure secrets. `--init-secrets` is fresh-install only and refuses any existing legacy project/volume. Prior to migration, stop old components using their **legacy** Compose identity while retaining containers for inventory: `docker compose -p observability -f app/tooling/observability/compose.yaml stop` and `docker compose -p agent-playbook-logging-smoke -f app/tooling/logging/compose.yaml stop`. Back up the Docker volumes and retain the legacy `.env`. After successful `--migrate`, run the matching legacy `docker compose -p <old-project> -f <component-compose> --env-file <legacy-env-for-langfuse> down` (omit `--env-file` for logging), never `-v`; then start the new project. Rollback after stopping the new project uses `docker compose -p <old-project> -f <component-compose> --env-file <legacy-env-for-langfuse> up -d` against the retained physical volumes. The Mac guide will replace angle-bracket placeholders with concrete commands for the observed project/context and require checking traces/logs before declaring success. No automated invocation deletes old containers or data.

Disposable semantics probe, performed with Docker Compose v2.40.3 and no daemon: create a temporary Compose file with top-level `name: legacy-name`, one service containing `TARGET: ${TARGET:?missing}`, and external volume `name: ${DATA_VOLUME:?missing}`. Run `TARGET=example DATA_VOLUME=existing_data COMPOSE_DISABLE_ENV_FILE=1 docker compose -p act-logs -f /tmp/m3-compose-probe.yaml config --format json`; result names project `act-logs` and external volume `existing_data`. Place synthetic `TARGET=ambient-only` and `DATA_VOLUME=ambient_data` in `/tmp/.env`, then run `COMPOSE_DISABLE_ENV_FILE=1 docker compose -p act-logs -f /tmp/m3-compose-probe.yaml config --quiet`; exit 1 reports missing `TARGET`, proving the ambient file was not used. This uses only synthetic data. Commands writing a real shared secrets file or Docker volumes remain unrun.

### Failure policy and verification boundary

Start order is logs then Langfuse; stop order reverses. `all` attempts both selected components and reports each result. A failure of one never tears down the other. `--start` is idempotent after preflight; `--stop` is idempotent and uses verified `docker stop` on the named project's containers without volume deletion. Each Docker/Compose mutation has a 300-second cap (project listing/inspect/version/info: 10 seconds each; `docker stop -t 30`: 45-second subprocess cap), engine readiness 10 seconds per check plus existing Mac launch wait up to 90 seconds, and each component health poll a 300-second monotonic deadline at 3-second intervals. Reuse Langfuse six-service state plus HTTP health and logging `/health` read-only check; report health as readiness, never ingestion proof. Exit 0 when all requested operations succeed, 1 for Docker/start/health/partial failure, 2 for configuration, credential or migration/preflight conflict; SIGINT returns 1. Never print Compose `config` output, secret-bearing errors, argv environments or unredacted logs. Explicit diagnostics and tests use synthetic sentinels.
