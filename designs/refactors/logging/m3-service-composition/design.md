## Shared configuration and credentials — confirmed 2026-11-18

All integrations use the selected shared application YAML and its existing local-overlay/environment precedence. VictoriaLogs has a documented section alongside Langfuse and CrewAI: retain the existing provider-neutral integrations.logging section for its application logging settings. Do not introduce a second overlapping integrations.victorialogs configuration or a provider-specific loader.

Non-secret settings belong in shared application configuration. Tokens, passwords and other secret values belong in the same external secrets file selected by secrets.file, already used for Langfuse credentials and available to other integrations. YAML contains named references rather than literal secrets. Future components follow this same rule.

The current default remains ~/.config/agent-playbook/secrets.env. M3 preserves existing project, package, CLI, file and folder names and user paths; any broader naming migration belongs to issue #56. Shared-secret consolidation uses the existing configured secrets.file path.

The selected direct local VictoriaLogs deployment currently requires no credentials. Document this explicitly; do not invent a token/password or add authentication middleware merely to populate the section. If a later approved deployment needs credentials, it uses the shared secrets mechanism.

### Existing infrastructure discrepancy and migration requirement

Current application documentation explicitly separates Langfuse application keys from app/tooling/observability/.env infrastructure secrets. Therefore the requested shared-file policy is a change to deployment configuration ownership, not a description of completed behavior.

Before implementation, inventory only documented key names and setup/management code, never read personal credential values. Specify how existing Langfuse database passwords, encryption keys and other infrastructure credentials are retained in the selected shared secrets file. Do not regenerate existing values, overwrite unrelated entries, or silently resolve conflicting values. Define an explicit conflict/migration procedure.

Compose receives only the values needed by the selected component through the minimal supported bridge from the existing loader. Shared storage of secrets does not authorize injecting every credential into every container. Avoid another independently editable credentials file, custom parser, credential discovery or config registry. Concrete Compose input mechanics and compatibility with existing Langfuse setup remain to be designed and verified.

## Technical design completion proposal (2026-11-18; awaiting Sharon's concrete approval)

The choices below complete the open technical questions for review. They are proposed contracts, not an extension of the earlier behavioral approval. No runtime change is authorized by this document alone.

### Ownership and entry point

Use two Compose invocations, never `include` or multi-file aggregation: `docker compose -p act-logs -f app/tooling/logging/compose.yaml` and `docker compose -p act-langfuse -f app/tooling/observability/compose.yaml`. A single checkout-only `app/tooling/services/manage.py` coordinates `--start`, `--stop`, `--status` with `--component logs|langfuse|all` (default `all`) and optional `--config PATH`; invoke from the repository root with `app/.venv/bin/python app/tooling/services/manage.py ...`. `all --start` selects enabled integrations; explicit component start still requires its enabled setting. `--stop` addresses the named project even after an integration is disabled; `all --stop` addresses both. `--status` reports both (or the requested component), including disabled and stopped, without treating disabled as a failure. The entry never runs during workflow execution. Keep the existing `agent-playbook langfuse` CLI spelling and direct `observability/manage.py` path as compatibility entry points delegated to the same component operations; `--check` keeps its existing read-only application check and hosted-endpoint behavior. Existing `--logs`, `--follow`, and `--open` remain Langfuse-only helpers. `--env-file` is a legacy import selector only, with clear migration guidance; it is never an ongoing second store. This is the narrow M3 bridge, not the M4 management CLI.

`-p` fixes project identity regardless of Compose file top-level `name`, shell `COMPOSE_PROJECT_NAME`, or caller directory. Explicit `-f` and `--project-directory` fix file resolution. Compose is invoked with a deliberately constructed environment (remove inherited Compose control/interpolation variables, then add only required selected values) and no `--env-file`; never pass credentials as argv. Keep each definition and its images/services/network/loopback bindings. Logging service name `victorialogs` is unchanged; Docker project is `act-logs`. Langfuse's six service names remain unchanged; Docker project is `act-langfuse`. Compose `config --quiet` validates without printing resolved secrets. Docker's [project-name precedence](https://docs.docker.com/compose/how-tos/project-name/), [interpolation rules](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/), [external volumes](https://docs.docker.com/reference/compose-file/volumes/) and [`down` behavior](https://docs.docker.com/reference/cli/docker/compose/down) support this split. Disposable Compose v2.40.3 probe: a file with `name: legacy-name`, `external: true` volume and interpolated environment resolved under `-p act-logs` to project `act-logs` and the supplied existing volume name; daemon access was unavailable, so no live migration claim.

### Shared loader and minimal schema

Use `app/src/agent_playbook/config/loader.py` and models; extract common base/local selection, `secrets.file` resolution, strict parser and environment precedence into internal helpers used by both workflow `load_configuration` and a narrow `load_local_services_configuration(path, component)` API. It reads selected YAML via `configuration_path`, sibling `.local.yaml`, selected secrets file and process environment in that order. It resolves the selected component only: an explicit logs-only operation does not resolve or require Langfuse project or infrastructure keys, including when Langfuse is enabled in YAML. For `all --start`, first resolve enabled flags with existing overrides, then resolve deployment values for enabled components. For stop/status, resolve selected config for display when possible but inspect project identity regardless of enabled flags; invalid/missing config yields exit 2 for start and a diagnostic for stop/status without blocking safe project inspection. Do not create a provider-specific parser or credentials registry. Keep workflow validation behavior and precedence intact.

Add optional `integrations.langfuse.local_service` containing `minio_port: 9090` and seven fixed named infrastructure references: `postgres_password: {env: POSTGRES_PASSWORD}`, `clickhouse_password: {env: CLICKHOUSE_PASSWORD}`, `redis_auth: {env: REDIS_AUTH}`, `minio_root_password: {env: MINIO_ROOT_PASSWORD}`, `nextauth_secret: {env: NEXTAUTH_SECRET}`, `salt: {env: SALT}`, `encryption_key: {env: ENCRYPTION_KEY}`. This block is relevant only for local deployment; application project `public_key`/`secret_key` remain separate. The Langfuse host port is the port of local loopback `base_url`; reject remote host, path and scheme for **local start** without changing hosted connection checks. Add optional `integrations.logging.local_service` with `retention: 7d` for the existing Compose retention; logging host port comes from the validated loopback `endpoint`. No VictoriaLogs credential reference is added. Keep fixed container ports, images and paths. Compose receives only `LANGFUSE_PORT`, `MINIO_PORT` plus seven Langfuse infrastructure values for Langfuse, or `LOGS_PORT`, `LOGS_RETENTION` for logging, and selected volume identifiers. Make Compose interpolation required for settings supplied by the bridge, eliminating stale defaults; validate bounded port/retention values in the shared models. Add a safe, documented default for optional deployment blocks so old YAML remains loadable. Settings keys and references are documented, never literal secret values.

### Credential consolidation and storage transition

Inventory the seven documented legacy names from tracked `setup.py`/`.env.example`; do not inspect user files in design work. Implementation offers `--migrate` on the shared entry (with optional `--legacy-env-file PATH`, default existing adjacent `.env`) as an explicit pre-start step. No automatic credential generation. Parse legacy file with the existing strict dotenv parser, require all seven nonempty values, and compare **effective** selected shared-file values including process overrides. If a name already exists with the same value, leave it; if different, stop before any write and report key names only. If a process override differs, stop and ask user to clear/resolve it. Missing/unreadable/malformed legacy or shared file stops without mutation. Append only missing names atomically using a mode-0600 temporary file in the selected file's directory, flush/fsync, then replace; preserve all unrelated lines/keys and create a private backup before replacement. A failed write retains original and backup. Do not print values, use shell sourcing, or put values in tracked files. Keep the legacy `.env` untouched as rollback evidence; once migration verifies data, tell the user to remove or archive it manually because it remains a second copy. The old `setup.py` is retained as legacy fixture/tool but not called by new start. A fresh local deployment requires explicit generation into the selected shared secrets file via a one-time safe initializer that writes only absent seven keys, refuses conflicts and preserves unrelated entries; retain existing `secrets.token_hex` sizes. This uses the existing loader/parser and setup generator, with no extra store.

Before **any** `up`, inspect Docker context, old and new project containers by Compose labels, and all expected named volumes. Old logging project is `agent-playbook-logging-smoke`, with `agent-playbook-logging-smoke_logs-data`; old Langfuse default project is `observability`, with five `observability_{postgres_data,clickhouse_data,clickhouse_logs,redis_data,minio_data}` volumes. A custom `COMPOSE_PROJECT_NAME` or different recorded project is supported only by explicit `--legacy-project NAME`, verified against container labels and exact mounted volume source/target pairs. Never infer an alternate project from volume name alone. If old containers are running, stop with instructions to use the old project's `down` without `-v` after backup; do not stop them automatically. If both old and new stacks exist or any volume mapping is partial, foreign, inconsistent or ambiguous, stop without `up`. For complete old volumes, bind the **existing physical names** in the new Compose files using required `external: true` and `name: ${...}` values. For a clean install, create the required physical volumes (one logging or five Langfuse) explicitly with `docker volume create --label ...`, then verify and bind them; do not claim empty new volumes are migrated data. Existing project never gets a replacement volume silently. Verify no other running container mounts selected volumes, and recheck immediately before `up` to reduce the race; document Docker's lack of an atomic lock and require Docker Desktop not to be operated concurrently. For an existing Langfuse stack, preserve the seven infrastructure values exactly so encrypted database/object data stays readable. `down` is project-scoped and never uses `-v`; no volume rm/prune or reset command is run. Record chosen volume mapping in a private, non-secret manifest beside the selected secrets file so repeat operations and stop/status use the same mapping; if manifest and Docker state disagree, fail closed. Back up Docker data before the manual transition; live Mac guide checks existing traces/records after restart. A new project name can coexist only when old containers are stopped and storage is uniquely assigned; old project containers remain available for rollback after new project is stopped.

### Failure policy and verification boundary

Start order is logs then Langfuse; stop order reverses. `all` attempts both selected components and reports each result. A failure of one never tears down the other. `--start` is idempotent after preflight; `--stop` is idempotent and uses `down` without volume deletion. Each Docker/Compose command has a 300-second cap, engine readiness 10 seconds per check plus existing Mac launch wait up to 90 seconds, and each component health poll a 300-second monotonic deadline at 3-second intervals. Reuse Langfuse six-service state plus HTTP health and logging `/health` read-only check; report health as readiness, never ingestion proof. Exit 0 when all requested operations succeed, 1 for Docker/start/health/partial failure, 2 for configuration, credential or migration/preflight conflict; SIGINT returns 1. Never print Compose `config` output, secret-bearing errors, argv environments or unredacted logs. Explicit diagnostics and tests use synthetic sentinels.

Current app and public guides remain untouched by this design-only PR. Implementation updates `app/application.yaml` placeholders/references, tooling READMEs, `app/docs/configuration.md`, `logging.md`, `langfuse-local.md`, `langfuse-connection.md`, docs index/discovery links and Atlas/progress from shipped evidence. No Stage 02 historical acceptance text is rewritten. Exact guarded logical amendments proposed for separate approval: principle 6 adds shared application YAML, selected external `secrets.file`, existing loader and future-integration reuse while retaining workflow ownership/environment overrides; root `AGENTS.md` adds that convention, required canonical key/reference documentation and credential preservation during migration; `designs/architecture.md` adds checkout-only two-project deployment coordination and loader-to-Compose bridge without runtime runner dependency; `designs/project-structure.md` places coordination at `app/tooling/services/` and deployment definitions at existing component paths, with config loader/models retaining validation. These additions do not transfer deployment orchestration into workflow execution. Each guarded file needs its own inspectable diff and Sharon's concrete approval before editing.
