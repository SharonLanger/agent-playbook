Correlation exists from the beginning and survives derivation; trace/span IDs are optional native enrichment.
2. Initially logs had to work by running Python alone. Starting another VictoriaLogs service was unwelcome. Structlog became the direction for reusable processing/context/exception/JSON machinery, with standard logging potentially owning files/rotation. Its value was more than appending dictionaries. Detailed design remained unfinished.
3. Storage and viewer were separate. JSONL was preferred; an existing embedded SQLite solution was acceptable if simpler. Select filters, query matching records, load them, then sort/filter locally. Separate CLI/Docker viewer startup was acceptable but must not gate recording. No viewer, indexing, retention, rotation or simultaneous-writer strategy was verified.
4. Agent A receives derived workflow context, helpers use that child, returning leaves the original parent without agent fields, and B receives another child. This context foundation exists; logger integration does not.
5. The original shared tracing/logging broker was rejected to preserve native Langfuse capabilities. A small replaceable logging wrapper remains an idea. Automatic Langfuse/CrewAI observation-to-log duplication is unresolved.
6. Error-level diagnostics do not force workflow failure. A recovered agent failure can coexist with parent success.
7. Constraints: local processing/storage, Apache 2.0 for new logging/viewer components (Langfuse separately accepted), existing open source, minimal custom code and independent replaceability.
8. Existing Docker usage reopens VictoriaLogs. Structlog may prepare records while VictoriaLogs stores/queries them. Whether local records survive service outage remains undecided.
9. Starting point: debugging requirements/context model established, storage/viewer choice reopened, logging API undesigned.
