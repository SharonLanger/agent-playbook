### R1 — connection preflight disables subsequent export

Locations: [connection.py](../../../app/src/agent_playbook/observability/adapters/langfuse/connection.py),
`create_client` / `check_connection` (reviewed lines 21–32, 42–43 and 60), and
[observations.py](../../../app/src/agent_playbook/observability/adapters/langfuse/observations.py),
`LangfuseSession.__init__` (line 29). The requested playground calls the check
before constructing its session in the same process.

The pinned Langfuse SDK **5.2.0** caches its resource manager by public key.
`check_connection` first creates a client with `tracing_enabled=False`, then
shuts it down. A later tracing-enabled client for the same public key reuses
that resource manager; shutdown has not removed the cached resource. No working
export pipeline is established by that sequence.

Observed with the real installed SDK and a local HTTP fixture:

1. Return a nonempty project response from `GET /api/public/projects`, using
   synthetic local keys and no real Langfuse account.
2. Run the unchanged playground in a fresh subprocess against that endpoint.
3. It exits zero, prints `outcome: success` and `Submission completed`, and
   prints a trace link. The fixture receives two project GETs and **zero POSTs**.
4. Control: in a separate fresh process, construct `LangfuseSession` directly,
   create/end an observation, flush and close. The fixture receives an OTLP POST
   to `/api/public/otel/v1/traces`.

This is SDK transport evidence, not proof of persistence in a Langfuse server.
It explains why the current example can look successful while sending no traces.
A standalone checker run in its own process is different: the problematic
sequence is preflight followed by tracing **inside the same process**.

Required correction: establish clear client/resource ownership so checking
credentials cannot disable or close a resource used by tracing. Add a maintained
regression using the actual pinned SDK and an independent loopback HTTP fixture:
authenticate, create/end a trace in the same process, flush, and assert a real
export request. Do not replace the SDK client with a fake for this regression.
Application tests must not import or execute the personal playground.

### R3 — export rejection is reported as submission success

Locations: `LangfuseSession.flush` in
[observations.py](../../../app/src/agent_playbook/observability/adapters/langfuse/observations.py)
(reviewed lines 50–51), and the requested playground's completion/reporting block
(reviewed lines 131–138).

Separate probe: bypass only the connection preflight to isolate R3 from R1;
retain the actual session, SDK and exporter. Have the local HTTP fixture answer
the OTLP request with **HTTP 400**. Observed:

- An actual export POST reaches the fixture and is rejected.
- SDK stderr reports `Failed to export spans batch code: 400, reason: Bad Request`.
- The script still prints `outcome: success`, `Submission completed`, and exits zero.

The arithmetic succeeding is valid; claiming successful submission is not. In
this case the SDK reports the export error without raising through `flush`, so
the script's exception handler cannot establish delivery. A returned URL is not
an ingestion receipt either.

Required correction: distinguish **mock execution outcome**, **export outcome**
and **trace visibility**. Define a bounded verification path and accurate exit
status for explicitly verifying delivery. Use a supported export-result signal
or bounded readback; do not assume a flush return means persistence. If visibility
cannot be checked, report it as unconfirmed. Add an actual-SDK rejection
regression, separate from the personal example. Retain deliberate mock-step
failures as a different result from infrastructure/export failure.
