## Acceptance and fixture rules

These stable RUN IDs belong to M4.2. They do not reuse CTX IDs or claim that M4.1 approval/results accept tracing. Cases describe the recommended RUN-D01–05 policies; finalize those decisions and this exact test revision before implementation. Once approved, a required case is not satisfied by a missing, skipped, xfailed, blocked, weak or unexecuted assertion. Preserve existing tests that already prove a requirement instead of adding duplicates.

Foundation: root's [final M4.1 review](history/context-final-review.md), published at `68166c94497bf388eb05250c38cccc43f732a0f4`, records runtime/design PASS at candidate `16c1580e96bd36945fa96b6ecfa8f9a563d53913` and an independent 43-test targeted pass. Documentation conflicts/duplicate D30 remain; PR #44 is unmerged. This evidence does not execute any RUN case or constitute Sharon's M4.2 acceptance.

Use the actual application runner, approved M4.1 context and native Langfuse SDK. A small public `TracerProvider(sampler=ALWAYS_ON)` plus `InMemorySpanExporter` passed through Langfuse's public constructor is the main export fixture. Retain the SDK's real processor and default filter; exporting a test-only OTel span through a different processor is not proof that the application's native observations survive. Use unique synthetic project keys or separate test processes to avoid SDK public-key resource caching between incompatible fixtures. Never manipulate SDK private caches in production or infer lifecycle safety from a fixture that does so silently.

Small spies may delegate into real construction to capture context identity, or inject one precise application/SDK failure. Do not mock both ends of the runner/SDK path and call that integration evidence. No new test framework, Docker requirement for ordinary tests, mutation-testing platform or blanket suite repetition is needed. Prefer existing loopback/auth/offline helpers where they satisfy the assertion; preserve their stronger negative controls and maintained regression cases.

Never read, search, import, run or use data from `app/examples/` or historical `sandbox/`. Original research/probe files are preserved evidence, not maintained test inputs; tests import actual candidate application modules and their own small fixtures. Synthetic child types test SDK correlation mechanics, not real agent/model behavior.

| RUN-13 | Metadata values at/over the SDK compact JSON length limit; repeated Python calls change tracing config | Fitting correlation/workflow/run strings remain exact on all emitted observations. Too-large/unsupported value causes fixed diagnostic and no invocation root, with unchanged business result under RUN-D05; no truncation/backfill/dropped mandatory key. Include quotes/Unicode whose JSON size differs from plain length. | RUN-14 | Sentinel secrets in raw JSON, valid business data/config, result presentation and nested original exception/cause | Examine actual exported root attributes, events, status description, name and resource data; sentinels absent, required identity/outcome intact. Check captured SDK/application diagnostics as well as export, including rejected HTTP response content |
| RUN-15 | Success, each failed phase and interruption outcome projection | Exact allowlist and correct fixed outcome/phase/severity; successful needs_work is completed, not ERROR. Raw type/message/traceback/exception repr and arbitrary configuration metadata absent. Unexpected projection errors preserve application outcome. RUN-12 reuses the existing SDK loopback approach where possible; it must execute this runner/client path. The test deadline is an evidence guard, not a new production timeout mechanism. A transport 200 only proves fixture delivery, not Langfuse ingestion. Do not add readback polling to every workflow to make this test pass. Capture failures without storing real credentials or private request bodies in reports.

RUN-13 is an M4.2 projection/configuration policy case, not a new M4.1 constructor validation requirement. Generated UUIDs remain sufficient for normal runner correlation. It also prevents a small SDK resource-cache behavior from silently sending the next invocation to a stale endpoint.
