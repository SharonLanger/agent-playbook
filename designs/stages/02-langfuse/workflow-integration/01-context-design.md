## 1. Goal, baseline and scope

Give each workflow invocation one typed application context. Pass it through the existing runner, factory, workflow constructor and CrewAI Flow. A child agent scope gets its own enriched data without changing the parent. An application correlation ID survives that derivation independently of tracing.

Inspected baseline: main `d12b5fc2867d3646b6fab2eb71f1447ff177d8c1`; planning PR #43 at `dc47e37ba44be90a66226c6952dc033057f66dc0` before this draft. Runtime pins remain Python >=3.13,<3.14, CrewAI 1.15.40, Pydantic 2.12.5 and Langfuse 5.2.0. Refresh the implementation base before coding; this draft does not assert compatibility with unseen later changes.

M4.1 includes the actual constructor/Flow wiring and its tests. It is not merely a new models file. M4.2 adds runner tracing; M4.3 enables the researched CrewAI instrumentor. M4.1 adds no Langfuse calls, instrumentation installation, logging, viewer, agent runtime, child-workflow launcher, distributed propagation, global active context or new dependency. Existing workflow output and error behavior stay unchanged.

D18/D19 settle composition and propagation. D25/D26 leave SDK trace/span identity and live SDK objects outside the initial context. D27 accepts a separate application correlation ID. Exact choices below are the proposed detailed contract for review. Drafting is authorized; implementation follows approval of this package and the file-specific amendments in section 9.

## 2. Definitions and identity

Create `app/src/agent_playbook/context/models.py` and a minimal package `context/__init__.py`. Both types live in models.py; import them from `agent_playbook.context.models`. The package depends only on the standard library. It does not import application, config, workflows, CrewAI, Langfuse, OpenTelemetry or execution adapters.

```python
from dataclasses import dataclass, field, replace
from uuid import uuid4


@dataclass(frozen=True, kw_only=True)
class ObservabilityContext:
    workflow_id: str
    workflow_run_id: str
    agent_type: str | None = None
    agent_run_id: str | None = None


@dataclass(frozen=True, kw_only=True)
class ExecutionContext:
    observability: ObservabilityContext
    correlation_id: str = field(default_factory=lambda: str(uuid4()))

    def for_agent(self, *, agent_type: str, agent_run_id: str) -> "ExecutionContext":
        return replace(
            self,
            observability=replace(
                self.observability,
                agent_type=agent_type,
                agent_run_id=agent_run_id,
            ),
        )
```

This small data-derivation method is the only added behavior. It centralizes preserving identity while setting both agent fields, using Python's existing replacement operation. It is not a reporting method, span scope or agent factory. Its name and signature are part of this draft, not an earlier accepted API.

| Field | Meaning and source | Lifetime |
|---|---|---|
| ExecutionContext.correlation_id | Application grouping ID; generated by the dataclass constructor using UUID4 when omitted | Fixed for the initial context and its descendants; may later be supplied to related workflow contexts |
| observability.workflow_id | Selected configured YAML ID, including aliases; supplied by runner | Fixed within one workflow invocation |
| observability.workflow_run_id | Fresh `str(uuid4())` supplied by runner for each invocation | Fixed through that invocation's agents/helpers; different on another invocation |
| observability.agent_type | Optional application role/category, supplied when deriving an agent scope | None at workflow level; child's own value below the agent boundary |
| observability.agent_run_id | Optional identity for one agent invocation, supplied by its eventual caller | Fresh per invocation, including A → B → A; helpers reuse it |

Place correlation_id on ExecutionContext because it describes application work and can be used by outputs, events or other consumers later. Do not duplicate it inside ObservabilityContext. Workflow/agent identities stay in the already agreed observability section; moving all identity into another class is unnecessary now.

Constructor defaults run only when a value is absent. Leave correlation_id as an ordinary constructor field with `init=True`; do not regenerate it in `__post_init__`, use an import-time UUID, or use `init=False` with a factory. `replace` must retain the existing value. Explicit construction with an existing correlation_id is supported for typed Python callers and tests. This alone does not add an incoming-ID CLI option or child-workflow execution API.

The model contains strings, None and a frozen nested dataclass, with no mutable collections. Frozen fields prevent ordinary assignment; this is an application programming contract, not a security boundary against deliberately bypassing Python's protections. No custom setters, serializer, Context ABC, Protocol or validation framework is needed. The selected workflow ID remains validated by existing selection. New IDs are generated internally; external/untrusted ID acceptance is outside M4.1. The typed constructors do not promise runtime rejection of every wrongly typed Python argument. Agent ID generation belongs to the eventual invocation caller, not to reading/copying context.

## 3. Runner and factory construction

Keep `run_workflow(workflow_id, raw_input, *, config_path)` and RunResult unchanged. Do not expose context through CLI output or add flags in this milestone.

Ordering in `application/workflow_runner.py`:

1. Existing configuration assembly and CrewAI startup configuration.
2. Existing registry import and selected-entry validation.
3. Inside the existing CONSTRUCTION try/except, create the context immediately before constructing the selected wrapper:

```python
context = ExecutionContext(
    observability=ObservabilityContext(
        workflow_id=workflow_id,
        workflow_run_id=str(uuid4()),
    )
)
workflow = construct_workflow(
    workflow_id, implementation, application.integrations.crewai, config,
    context=context,
)
```

4. Existing JSON decoding, prepare, execute, validate_output and serialize_output, in the same order and with the same error boundaries.

Every independent call creates fresh correlation and workflow-run values, even in the same Python process and for the same workflow ID. Nothing is created at module import. Configuration/selection failures before step 3 have no context; this milestone does not add logging for them. If context construction unexpectedly fails, the existing CONSTRUCTION execution error and cause preservation apply. No new failure phase or exception class.

Add required keyword-only `context: ExecutionContext` to both `construct_workflow(...)` and `create_workflow(...)` in `application/workflow_factory.py`. Preserve their existing positional parameters. `create_workflow` still selects then calls `construct_workflow`, forwarding the supplied context. `select_workflow` is unchanged. Both factory functions are pass-throughs: no default context, ID regeneration, copying or mutation. Typed direct callers must supply a context matching the selected workflow ID; the runner guarantees this in the supported invocation path. No second identity-validation framework is introduced.

Changing these internal constructors is deliberate. Update maintained direct callers, fakes, fixtures and examples in official documentation. Do not scan or repair personal `app/examples/`. Old installed releases remain self-contained; no compatibility shim or optional-context fallback is required.

## 4. Workflow ownership and CrewAI Flow propagation

In the existing Workflow ABC, extend the keyword-only constructor:

```python
def __init__(
    self, *, settings: CrewAISettings, config: Mapping[str, object],
    context: ExecutionContext,
) -> None:
    self._context = context
    # Existing settings, config and lifecycle initialization remain.

@property
def context(self) -> ExecutionContext:
    return self._context
```

The property has no setter. All three concrete wrappers add the same required constructor argument and forward it through super(). No changes to final lifecycle methods, their hook signatures, generic result types, statuses, validation rules or result/error serialization. A wrapper continues to represent one invocation and cannot be reset/reused for another run.

During valid `_prepare`, each wrapper passes `context=self.context` into its existing Flow constructor alongside its current state/tracing/display arguments. Preserve lazy Flow imports and validation-before-construction. Invalid input must still prevent Flow construction and kickoff. `_execute` continues to call `self._flow.kickoff()`; no context is inserted into kickoff inputs or state.

### Flow storage contract

The pinned CrewAI Flow is a Pydantic model and already has a framework `execution_context` field. Our ExecutionContext is a separate application type. Do not populate/replace that framework field, use it as an alias, or add our context as a serialized Pydantic field.

Each maintained Flow declares `_app_context: ExecutionContext = PrivateAttr()` and exposes a read-only `context` property. Its constructor consumes our required keyword-only context, calls the existing superclass constructor with only framework arguments, then assigns `_app_context`. No business method runs during this assignment. Access is guaranteed after construction, including all kickoff methods; exposing context to framework construction callbacks is not a requirement.

Use explicit typed constructor parameters for the application-supported arguments:

| Flow | Additional keyword-only parameters, besides required context |
|---|---|
| StepSequenceFlow | initial_state: FlowState \| None = None; tracing: bool \| None = None; suppress_flow_events: bool = False |
| SharedStateFlow | initial_state: NumberState \| None = None; tracing: bool \| None = None; suppress_flow_events: bool = False |
| ConditionalRouteFlow | initial_state: ScoreState \| None = None; tracing: bool \| None = None; suppress_flow_events: bool = False |

This preserves maintained no-state/state/tracing/display calls and allows subclasses of those state types. No catch-all Any kwargs, new Flow base class, mixin or framework engine is required. New unneeded CrewAI constructor features are not exposed by this milestone. Do not alter installed third-party source or override kickoff, scheduling, routing or serialization to carry context.

Representative body for SharedStateFlow (keep its existing decorated methods):

```python
_app_context: ExecutionContext = PrivateAttr()

def __init__(
    self, *, context: ExecutionContext,
    initial_state: NumberState | None = None,
    tracing: bool | None = None, suppress_flow_events: bool = False,
) -> None:
    super().__init__(
        initial_state=initial_state,
        tracing=tracing,
        suppress_flow_events=suppress_flow_events,
    )
    self._app_context = context

@property
def context(self) -> ExecutionContext:
    return self._app_context
```

The factory, wrapper and Flow retain the identical context reference. A decorated method may read `self.context.correlation_id` or `self.context.observability.workflow_run_id`. Pure arithmetic/string utilities do not need new unused parameters. A helper that actually needs context can receive it explicitly. Do not add prints merely to demonstrate access.

CrewAI/Pydantic shape was inspected in the installed pinned source. The constructor pattern still needs the actual-runtime tests in the companion test cases; source inspection is not a claim those tests passed. PrivateAttr avoids ordinary model serialization, not all possible copying/pickling of a Flow. Persistence/resume and generic Flow cloning remain outside scope.

## 5. Derivation and lifecycle

```python
reviewer_first = workflow.context.for_agent(
    agent_type="reviewer", agent_run_id="review-1"
)
coder = workflow.context.for_agent(agent_type="coder", agent_run_id="code-1")
reviewer_second = workflow.context.for_agent(
    agent_type="reviewer", agent_run_id="review-2"
)
```

Each call creates a new outer and inner context. All three retain the parent correlation_id, workflow_id and workflow_run_id. The parent still has no agent fields. Helpers within reviewer_first can receive that exact child reference; a deeper ordinary method does not imply another ID. Returning normally or by exception requires no metadata cleanup or copy-back because the parent was never changed. This says nothing about later SDK scope cleanup.

No agent is implemented here. The for_agent helper accepts identity rather than deciding whether a client/runtime is reused. It does not create clients, choose prompts/tools, start processes, store a mutable current agent or select an adapter's constructor/run interface.

To represent a future related workflow, a caller can construct another ExecutionContext with the same correlation_id and fresh ObservabilityContext workflow/run values; agent fields default back to None. M4.1 tests this data capability only. It does not implement nesting, scheduling or cross-process transport. A correlation ID is neither a Langfuse trace ID nor a retry/idempotency key. Matching metadata does not merge traces or establish parentage.

## 6. Extension, privacy and deferred work

Pass the whole context through intermediary signatures. Add future fields at their definition and producer/consumer; the nested replace operation preserves unspecified normal fields. New required semantics can still require callers to supply a value. Future mutable fields need explicit isolation review; do not add a generic dict now.

Keep existing settings/configuration on their current route. No credentials, inputs/outputs, exceptions, cost totals, SDK handles, sessions, step IDs, trace/span IDs or empty future sections enter this schema. Later telemetry code explicitly selects safe fields. A generic asdict(context) exporter is not introduced. The observability section carries data; it has no logging/tracing methods.

Deferred without blocking M4.1: client startup/flush/outages; trace binding and error reporting; native metadata projection; CrewAI instrumentation and masking; logs/viewer; real agents/usage/scores; background tasks/process transport; child-workflow execution. M4.2/M4.3 must resolve their own questions before implementation. The accepted no-broker provider-rule exception is needed before tracing integration, not to add these provider-independent data classes.
