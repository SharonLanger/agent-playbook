## 9. Agreed classification and assessment — accepted in iteration 3

The goal is to separate technical necessity, project-specific necessities and justified future preparation. Sharon accepted these definitions and assessment criteria on 2026-11-14. Individual new capability details and their proposed priorities still need review; accepting the rubric does not approve an unseen implementation design.

| Class | Meaning | Agreed treatment |
| --- | --- | --- |
| A — Essential to operate | Without this, the selected block cannot perform its basic job: produce a usable trace or save a log record. | Required in the first working version of that block. |
| B — Essential for Agent Playbook | A bare integration could work without it, but it would violate an agreed project requirement or required correctness/robustness. | Also required for project acceptance; not a nice-to-have. |
| C — Small preparation worth doing now | A limited addition avoids credible, materially larger future changes for an identified scenario. | Include only with a specific future use, small current cost and clear cost of postponement; no speculative framework. |
| D — Useful later | Helpful capability that can be added later without an expensive rewrite, or whose need is still uncertain. | Defer explicitly; retain its question/trigger. |

Cross-cutting constraints such as local-only application logging, no extra required logging service and licensing are pass/fail conditions. Do not average them away in a convenience score. A proposal outside scope or conflicting with a constraint is marked excluded/conflicting, not merely low priority.

For every capability, later record:

1. Applies to: Langfuse, local logger or both. Shared requirement does not imply identical implementation in both.
2. Observable outcome and omission consequence: what works, and what breaks or is lost without it.
